# Auth-service replay protection investigation

Status: stage 1 implemented. A shared atomic backend remains future work.

## Stage 1 implementation

The auth service now requires an injectable `ReplayStore` through
`AuthService::new`. All callers, including production, must supply a store; the
service does not create a hidden process-local default. `MemoryReplayStore` is
available for local development and tests. It evicts entries in expiry order,
enforces a configurable capacity, and rejects new reservations when full rather
than evicting unexpired nonces. Store results distinguish consumed, replayed,
and expired outcomes from store failures. Releases carry a reservation identity,
so a delayed release cannot remove a newer reservation for the same nonce.
Metrics cover replay hits, evictions, store failures, capacity rejections, and
retained entries.

## Pre-stage-1 behaviour

Before stage 1, `AuthService::new` always constructed a new in-memory replay
cache. The cache was not part of `AuthServiceConfig` and could not be supplied by
the caller.

The cache stores `(token_id, nonce) -> expires_at` in a
`parking_lot::Mutex<HashMap<...>>`. Verification calls `consume` only after the
token, scope, expiry, policy, and signature checks succeed. It then updates the
token's `last_used_at` through the shared `TokenStore`.

`consume` rejects an expired signed request, locks the whole map, calls
`retain` to evict entries whose expiry is not after `now`, rejects a duplicate
`(token_id, nonce)`, and inserts the new pair. `release` removes the pair again
when a later step fails, such as a transient token-store update error. Existing
tests intentionally rely on that retry behaviour.

The nonce is a random 32-character alphanumeric value generated by
`OrderRequestContext::generate`. Replay identity is `(token_id, nonce)`, not the
request body or an order identifier. Entries are retained until the signed
`expires_at`. The cwasm invoker currently configures five-minute signature
validity, but `AuthServiceConfig` only enforces a one-second minimum and has no
upper bound.

## Findings and risks

1. **Process-local:** each `AuthService` owns a separate map. Two verifiers
   using the same Vault token store can each accept the same signed envelope.
2. **Restart-sensitive:** restarting a verifier forgets every consumed nonce
   while the signature remains valid, so the replay window is the remaining
   signature lifetime.
3. **Token store does not help:** Vault makes token records shared and uses
   compare-and-swap for updates, but stores no nonce history.
4. **O(n) sweep on the hot path:** `retain` scans every unexpired entry while
   holding a single mutex, serializing all verifications.
5. **Unbounded state:** there is no capacity limit, background eviction, or
   upper bound on `signature_validity`. Memory grows with request rate times
   validity, and an authenticated client can increase it with valid requests.
6. **No observability:** there are no metrics for cache size, evictions,
   replay hits, or store failures.
7. **`release` needs stronger semantics when shared:** an unconditional delete
   could remove a newer reservation for the same nonce. A shared backend needs
   compare-and-delete, a reservation token, or a transaction.
8. **Replay protection is not order idempotency:** downstream deduplication can
   prevent duplicate orders, but the auth service would still accept the same
   signature twice.

## Requirements for an improved design

- Atomically consume a nonce across all verifier instances.
- Survive restarts and rolling deployments.
- Retain nonces only until the signed expiry, with a configured maximum.
- Preserve retry after a transient token-store failure.
- Distinguish a replay from an unavailable replay store, and fail closed by
  default when replay state cannot be checked.
- Be injectable for tests and deployment-specific backends.
- Bound memory, give predictable latency, and expose basic observability.
- Avoid secrets or unnecessary signed data in replay keys and logs.

## Options

### A. Harden the local cache only

Replace the O(n) `retain` sweep with expiry-ordered eviction (map plus min-heap,
time wheel, or an expiring-cache library). Add a capacity bound and metrics.

This is low risk and fixes the hot-path scan, but does not address multiple
instances or restarts. It is only a transitional/local improvement.

### B. Add an injectable replay-store abstraction

Introduce a trait such as:

```text
trait ReplayStore {
    async fn consume(key, expires_at, now) -> Result<ConsumeResult, ReplayStoreError>;
    async fn release(reservation) -> Result<(), ReplayStoreError>;
}
```

Provide an in-memory implementation for local development and tests. Require
callers to pass the store to `AuthService::new` so production cannot
accidentally rely on process-local state.

This removes the hard-coded dependency, enables shared backends, makes store
errors explicit, and lets tests model multiple verifier instances. By itself it
does not change the default's security properties. The trait should be async
because a shared backend performs I/O, and `release` should carry a reservation
identity for safe compare-and-delete.

### C. Use a shared atomic replay store

Use a shared store as the source of truth. The key should include at least the
token ID and nonce, for example `auth-replay:<token-id>:<nonce>` or a hashed
equivalent, with a TTL equal to the signed expiry.

| Backend | Atomic primitive | Advantages | Trade-offs |
| --- | --- | --- | --- |
| Redis/Valkey | `SET key value NX PX <ttl>` | Fast, simple, per-key TTL, good metrics | New HA infrastructure, network dependency, TLS/auth, cost |
| DynamoDB | Conditional `PutItem` with `attribute_not_exists` and TTL | AWS-native, already used by the run store, durable | Per-request cost, higher latency, TTL deletion is best effort |
| NATS KV | `create` when absent, bucket or per-message expiry | Already used by the data plane | Current wrapper lacks per-key TTL; verifier gains a NATS dependency |
| Vault KV | `cas=0` create | Already used for tokens | Not a high-throughput replay store; no suitable per-key TTL/cleanup |
| SQL | Unique constraint or transaction | Strong semantics | Extra operational dependency and latency |

For Redis/Valkey, `release` should use compare-and-delete keyed by the value
written at consume time. For DynamoDB, include the reservation value in the
conditional delete. Never use an unconditional `DEL` or `DeleteItem`.

This fixes the multi-instance and restart gaps and scales independently of
verifier lifetime. It adds an availability dependency on every verification,
requires an explicit outage policy, and needs configuration, credentials,
health checks, and runbooks. A local recent-hit cache can avoid repeated shared
lookups for obvious duplicates, but must not be authoritative.

### D. Store a bounded replay window in the existing token record

Extend `TokenStore` with an operation that atomically records use and consumes
a nonce, or reuse the existing compare-and-swap update by adding a bounded set
of expiring nonce digests to `TokenMetadata`.

Typical flow: hash the nonce (for example SHA-256), add the digest and expiry to
the token's unexpired window, prune expired entries, and call `TokenStore::update`
with the expected token. A successful CAS consumes the nonce; a conflict is
retried. A failed update leaves the nonce unconsumed, so no separate `release`
is needed.

This uses state that is already shared and durable, needs no separate replay
service, and fits the existing CAS retry loop. However, it grows every token
record and must respect token-store record-size limits. Pruning is O(window
size) per update, high per-token request rates increase CAS conflicts and write
amplification, and Vault KV is not designed for high-frequency mutable
documents. Enforce a hard bound and reject when it is exceeded rather than
silently dropping replay state.

This is attractive for low-to-moderate per-token throughput or as a stopgap
when a new service is not feasible. It is a poor fit for very hot tokens or a
large maximum signature lifetime.

### E. Use a monotonic counter or one-time credential

Put a per-token counter in the signed request and maintain the expected counter
in shared token state. Accept only a counter greater than the last accepted one.
This gives O(1) replay state, but changes the signing protocol and requires
signers to allocate counters atomically. Distributed counter allocation,
rollback, gaps, and migration need careful design. This is a longer-term
protocol redesign.

### F. Route all verifications for a token to one process

Sticky routing or a single verifier per token preserves the local fast path,
but does not survive restarts and makes correctness depend on routing. It also
reduces availability and deployment flexibility. Not recommended.

### G. Rely on downstream order idempotency

An idempotency key in the order payload can prevent duplicate exchange orders,
but the auth service still accepts the replayed signature. It should complement
replay protection, not replace it, and only works if every downstream operation
is genuinely idempotent.

## Comparison

| Option | Cross-instance | Survives restart | Removes O(n) scan | New infrastructure | Main use |
| --- | --- | --- | --- | --- | --- |
| A. Harden local cache | No | No | Yes | No | Transitional/local |
| B. Injectable abstraction | No | No | Depends on implementation | No | Enables shared options |
| C. Shared replay store | Yes | Yes | Yes, for local cache | Usually yes | Recommended production direction |
| D. Replay window in token store | Yes | Yes | Per-token pruning | No | Lower-throughput deployments |
| E. Monotonic counter | Yes | Yes | Yes | No, but shared counter | Protocol redesign |
| F. Sticky verifier | Only while stable | No | Yes | No | Not recommended |
| G. Downstream idempotency | N/A | N/A | N/A | Depends | Defence in depth |

## Recommendation

Use a two-stage approach.

**Stage 1: make replay state injectable and remove the current hot-path cost.**
Add a `ReplayStore` abstraction, supplied explicitly by every caller, with an
in-memory implementation for local development and tests, expiry-ordered
eviction and a configured capacity bound, metrics for hits/evictions/store
failures/size, explicit replay-versus-store errors, and reservation-safe release
semantics.

**Stage 2: use a shared atomic backend in production.** Preferred order,
subject to operational constraints:

1. Redis/Valkey, if a highly available shared cache can be operated;
   `SET NX PX` maps directly to the required atomicity and TTL.
2. DynamoDB, if avoiding a new service matters more than latency; use a
   conditional put with TTL and an explicitly stored expiry.
3. A bounded token-record replay window (Option D), if per-token throughput is
   modest and no new backend is acceptable.
4. NATS KV or Vault only after validating their TTL, throughput, and failure
   semantics; their current primitives are not an obvious fit.

The shared store must be authoritative. A local cache may only be a fast
recent-hit cache. Longer term, consider a protocol-level monotonic counter or a
combined token-store transaction that consumes the nonce and updates token
usage atomically, plus downstream order idempotency as defence in depth.

## Implementation notes for a follow-up

- Require the replay store at `AuthService` construction; do not add a hidden
  process-local default for backwards compatibility.
- Model the replay key as an owned value instead of cloning two `String`s per
  call.
- Use signed `expires_at` for the backend TTL and cap retention with a
  configured maximum validity.
- Fail closed when replay state is unavailable; avoid silent "allow on error".
- Make `release` compare the reservation value or revision before deleting, and
  test a delayed release racing with a later consume.
- Test two `AuthService` instances sharing one fake store, restart behaviour,
  expiry cleanup, per-token nonce scope, store outage, and the existing retry
  path.
- Do not log full signatures or token secrets.
- Document any shared backend's configuration and failure behaviour in
  `docs/environment-variables.md`.

## Open questions

1. Where do production verifiers run, and how many can verify the same token
   concurrently?
2. What are the verification latency and availability budgets?
3. Should replay-store unavailability reject all order requests, or is a
   separately audited degraded mode required?
4. What is the maximum supported `signature_validity`, and can it be reduced?
5. Is downstream order placement already idempotent on a request/order ID?
6. Are verifiers single-region? Multi-region needs a globally consistent replay
   decision or region-scoped signing.
7. Is expected per-token throughput low enough for a token-record replay window,
   or is a dedicated store required?
